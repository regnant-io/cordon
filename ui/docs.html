Cordon API

v2.0.0 — Private Inference Engine

Overview

Cordon is a privacy-preserving AI inference engine. Every request is processed inside a verified Trusted Execution Environment (TEE). Model weights are encrypted at rest with AES-256-GCM. Every inference event is written to an immutable, hash-chained audit log before the response is returned.

Cordon is not an inference engine itself — it is a security and privacy layer that wraps any OpenAI-compatible backend (llama.cpp, vLLM, Ollama). The backend does the compute; Cordon provides attestation, encrypted weights, audit, and isolation.

All endpoints are under /v1/. The base URL is the address Cordon is listening on, e.g. http://localhost:8443.

Authentication

In development mode, pass your client ID in the x-client-id header. In production, mTLS client certificates are used — the client ID is extracted from the certificate CN field.

x-client-id: my-app

Unregistered clients receive a default policy: all models permitted, 60 req/min, 4096 max tokens per request. Register a named policy to restrict model access or set custom rate limits.

POST /v1/inference

Run a chat completion through the full Cordon security pipeline: identity check → rate limit → audit pre-write → TEE inference → output filter → covert channel detection → timing normalization → audit post-write → signed response.

Request

{
  "model_id": "llama-3.2-3b-instruct-q4_k_m",
  "messages": [
    { "role": "system",    "content": "You are a helpful assistant." },
    { "role": "user",      "content": "Hello!" }
  ],
  "inference_params": {
    "max_tokens":         512,
    "temperature":        0.7,
    "top_p":              0.9,
    "top_k":              0,
    "stop":               [],
    "repetition_penalty": 1.0
  },
  "session_id":      null,
  "timeout_seconds": 120
}

  "client_id":     "my-app",
  "usage": {
    "prompt_tokens":     36,
    "completion_tokens": 25,
    "total_tokens":      61
  },
  "choices": [{
    "index":         0,
    "message":       { "role": "assistant", "content": "..." },
    "finish_reason": "stop"
  }],
  "content_policy":  { "triggered": false, "rules_matched": [] },
  "covert_channel":  { "anomaly_detected": false, "anomaly_score": 0.0 },
  "signature": {
    "enclave_key_id": "ephemeral-2b54a1b1",
    "algorithm":      "ed25519",
    "value":          "hex...",
    "signed_fields":  ["request_id","output_hash","model_id","timestamp","mrenclave"]
  },
  "enclave_info": {
    "tee_type":         "simulation",
    "cordon_version":  "2.0.0",
    "mrenclave":        "hex..."

}

The signature is an Ed25519 signature over request_id + output_hash + model_id + timestamp + mrenclave. Verify it against the enclave ephemeral key from the attestation report.

For multi-turn conversations, pass a session_id UUID to maintain KV cache context across requests. Sessions are isolated per client — cross-client session access returns 401.

Health

GET/v1/health — Basic liveness check, no auth required.

GET/v1/health/detailed — Full node status: TEE state, inference backend, active requests, latency percentiles, audit chain status, integrity monitor, and security alerts.

Attestation

Attestation lets clients verify the exact code running inside the TEE before sending sensitive data. The MRENCLAVE is a SHA-256 hash of the enclave binary — any code change produces a different value.

  • GET/v1/attestation — Current attestation report with MRENCLAVE, PCR values, and combined hash.
  • POST/v1/attestation/verify — Submit a nonce; server returns a fresh report bound to that nonce (prevents replay attacks).
  • POST/v1/attestation/refresh — Trigger re-attestation.
POST /v1/attestation/verify
{ "nonce": "your-random-nonce" }

Models

GET/v1/models — Lists all encrypted model bundles in the store with their status.

Possible statuses: encrypted (on disk, not loaded), ready (decrypted and loaded), tampered (integrity check failed).

Models are provisioned offline using cordon-provision encrypt and placed in the bundle directory. The node discovers bundles on startup by scanning for manifest.json files. In dev mode with an HTTP backend, the model_id is passed directly to the backend and does not need to match a registered bundle.

Audit

Every inference request generates two audit entries: one before processing (intake) and one after (completion with output hash). The log is append-only, hash-chained, and signed with an Ed25519 key generated at node startup.

  • GET/v1/audit/tail?n=10 — Last N log entries (max 1000).
  • GET/v1/audit/verify — Verify the entire chain integrity.
  • POST/v1/audit/anchor — Returns the current Merkle root for external anchoring.

Errors

All errors return a JSON body with an appropriate HTTP 4xx/5xx status:

{
  "error":      "error_code",
  "message":    "Human readable description",
  "request_id": "uuid or null"
}

Common error codes:

  • auth_failed — Invalid client ID, expired cert, or suspended client
  • rate_limited — Too many requests or tokens per minute
  • inference_failed — Backend unreachable or returned an error
  • content_policy_violation — Output blocked by content filter
  • model_not_found — Bundle ID not in model store
  • quarantined — Node is in quarantine mode (tamper detected)
  • audit_write_failed — Fatal: audit log write failed, request rejected
