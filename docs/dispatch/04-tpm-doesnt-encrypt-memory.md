# Dispatch Entry

**Title**: TPM Doesn't Encrypt Memory  
**Slug**: tpm-doesnt-encrypt-memory  
**Image URL**: /img/dispatch/confidential-vms.png  
**Excerpt**: Industry conflates "hardware attestation" with "confidential computing." TPM proves boot integrity but does NOT encrypt memory. The operator with root can still read prompts from RAM. For actual memory confidentiality, use SEV-SNP, TDX, or Nitro.

---

## Body

There's widespread confusion about what TPM attestation actually protects. Marketing says "hardware attestation ensures confidentiality." This is **false**.

### What TPM Actually Does

TPM 2.0 attestation proves **how a machine booted**:
- These PCR values (hashes of boot components)
- This firmware version
- This Secure Boot state
- At this time

It does **not** prove:
- Memory is encrypted
- The operator cannot read RAM
- Prompts are private from the host

**Analogy**: A tamper-evident seal on a glass box proves the box hasn't been opened. It doesn't make the contents invisible through the glass.

### The Operator Can Still Read Memory

Even with TPM attestation, an operator with root access can:

```bash
# Attach debugger
pid=$(pgrep cordon)
sudo gdb -p $pid -batch -ex 'dump memory /tmp/dump.bin 0x7f0000000000 0x7f0010000000'

# Search for sensitive data
strings /tmp/dump.bin | grep "secret prompt"
```

This works because:
- TPM attests the **code** (PCR values are hashes of binaries)
- Code runs in **plaintext RAM**
- Root can read any process's memory

### When You Need Actual Memory Confidentiality

Use **confidential VMs**:

**AMD SEV-SNP**:
- Guest memory encrypted with per-VM key
- Key generated by Platform Security Processor (PSP), not accessible to hypervisor
- CPU decrypts on access; data in DRAM is always ciphertext
- Hypervisor reads guest memory → sees ciphertext only

**Intel TDX**: Similar hardware-encrypted guest memory, key managed by TDX module

**AWS Nitro Enclaves**: Enclave memory isolated from parent instance

### The Distinction Matters

**For sovereign AI**:

| Requirement | TPM 2.0 | SEV-SNP / TDX / Nitro |
|-------------|---------|---------------------|
| "Prove the software is unmodified" | ✅ Yes | ✅ Yes |
| "Operator cannot read my prompts" | ❌ No | ✅ Yes |
| "Memory is confidential" | ❌ No | ✅ Yes |

**Government handling classified data**: TPM is insufficient. Need SEV-SNP or equivalent.

**Central bank processing market data**: TPM is insufficient. Need confidential VMs.

**Healthcare with patient records**: TPM is insufficient if "operator cannot see PHI" is a requirement.

### What We Do

Cordon supports both, but **documents them distinctly**:

```toml
[attestation]
measurement_source = "tpm2"      # Boot integrity only
# OR
measurement_source = "sev_snp"   # Boot integrity + memory confidentiality
```

**Fail-closed validation**: A configuration claiming memory confidentiality without SEV-SNP/TDX/Nitro is **refused at startup**. We won't silently degrade the guarantee.

Every attestation response includes:
```json
{
  "measurement_source": "sev_snp",
  "memory_confidential": true,
  "operator_can_read_memory": false
}
```

### Cost vs. Benefit

**SEV-SNP / TDX**:
- **Cost**: More expensive instances (AWS c6a/m6a, Azure DCsv3), 5-10% performance overhead
- **Benefit**: Architectural memory confidentiality, no operator trust required

**TPM**:
- **Cost**: Negligible (most servers have TPM)
- **Benefit**: Boot integrity, firmware validation
- **Limitation**: No memory confidentiality

**Recommendation**: Use TPM for Sovereign Cloud mode (client VPC, operator semi-trusted). Use SEV-SNP for Vault/Island/Dark modes (operator untrusted or adversarial).
